What a mistake costs

Finance calls this dunning. One unpaid invoice, from its first reminder until it is paid or a person takes it, is a case. A case lasts weeks and spends almost all of them waiting.

Dunning (everyday word: collections) is chasing unpaid invoices. It runs in two directions. Outbound is the reminders we send on a schedule: a friendly email before the due date, firmer notices after it, and a final notice that a person approves. Everything on that side is dates, amounts and rules. Inbound is what customers write back, whenever and however they like, and someone has to read it and decide what it means.

A case is one unpaid invoice moving through that process. Mistakes are expensive: a wrong amount, a commitment nobody meant to make, or account details sent to the wrong address can turn into a complaint or a legal problem.

A case lasts weeks and spends almost all of that time waiting: for a date, a reply, a payment, or a person's approval. No code is running while it waits, so everything about the case has to be saved (in the lab, a row in the cases table with the time of its next wake-up), and whatever wakes it up has to read the case again first, because the balance or the schedule may have changed in the meantime.

When a message goes. How a case escalates. Any amount. The balance.

The design rule for the whole system. In the collections engine the model has two jobs: it writes the wording of a reminder, and it reads a customer's reply into one of six labels (a promise to pay, a dispute, and so on). The harness, the code around the model, does the rest: it decides which reminder goes, when and to whom, checks every dollar figure in a draft (and sends a fixed template if one is wrong), applies a fixed action for each label, and records every decision.

Four decisions never belong to the model: when a message is sent, how a case escalates, any amount of money, and the balance. Those come from code, the policy and the ledger.

The question is where the reminder schedule is written down, because that decides what a change costs. Take one request: an extra SMS for retail, the day before the due date.

  • In code: each reminder is a branch (if day == 3: …). Simple with one schedule; each new schedule adds branches, and each change is a deploy.
  • In a workflow tool: the reminders are boxes on a canvas that the business can edit without a developer. But each box is a reminder, so rules that apply to every message (quiet hours, weekends, the weekly cap) have to be repeated in every box. Most such tools keep a case that is already running on the version it started with.
  • In a record with a version: the schedule is data, so the SMS is one more row and the version goes from 4 to 5. You choose what running cases do; the lab's engine has them read the newest version the next time they wake. The cost: the path is less visible than a drawing, so you build a preview ("what will this customer receive next month?"), and a new kind of action, such as a new channel, still needs code.

Behind the choice: a collections system holds three things that change at different speeds. How a step is carried out changes rarely and belongs in code; the schedule changes whenever someone asks; where each case is changes every hour and belongs in the database. Keeping them apart keeps a cheap change cheap. The lab keeps one record per schedule in policies.json.

The two boxes are slide 4's: the model writes a reminder's wording and reads a reply. Code picks every next step.

The pre-read described four shapes for a system that uses a model, from least freedom to most: a prompt (one call), a chain (a few calls in a fixed order, with no branches), a workflow (steps with branches that code decides) and an agent (the model decides the next step, in a loop with tools).

The collections engine is a workflow. Code decides which reminder is due, when it may go out, to whom, and what a customer's reply changes. The model works in two places only: it writes the wording of a reminder, and it reads a reply into a fixed set of labels. An agent would be worth it for a step that has to explore, for example searching a customer's history to answer a question, and then it would be read-only and run with a step budget. Nothing in this engine needs that.

The second piece built live: the pass in engine.py, the single entry point evaluate(case_id, trigger). Every event that wakes a case, whether a timer, a payment, a customer's reply or a person's decision, goes through it. Does the stored thing say send the final notice or look at this case?

The lab's answer: the middle column, next_due_at on the case row.

Between two reminders a case does nothing for days: in the retail schedule, eleven days separate the second notice (day 10) from the final one (day 21). The question is what remembers the case in the meantime, and what that memory says. A job booked for later sits on a queue as "send Initech's final notice on 27 November" (Celery's eta, BullMQ's delay and Sidekiq's perform_in work this way). It survives a restart, but some queues are built for delays of hours rather than weeks, and when anything changes the job has to be found and rebooked, unless all it does when it fires is re-read the case. A row with a date stores when to look next on the case itself ("look at Initech again on 27 November"), and a small worker or a cron job regularly asks the database which dates have passed. It needs a process running and watched, and at large scale the dates often move into a queue.

A durable workflow engine, such as Temporal, AWS Step Functions or Inngest, is a platform that saves a running workflow's place, so a step can pause for weeks and resume after a crash; a payment or a reply reaches the waiting run as an event. It needs the platform, and changing a workflow while runs are waiting inside it needs versioning. All three survive a restart. The deeper difference is in the callout: a stored order to send acts on what was true when it was booked, while a stored "look at this case" makes the system check what is true when it wakes. The lab uses the middle column: the case row's next_due_at, read by worker.py.

The worker, worker.py, is a loop: write a heartbeat, ask the engine to wake every case whose next wake-up has passed, sleep a second, repeat. A wake-up is a question, not an order: the worker never sends anything itself; every case it wakes goes through the same entry point as any other event.

In class the worker was started, the clock moved four days (the first notices went out), the worker was killed, two simulated days passed, and the worker was started again. Umbrella's first notice (business clients get theirs on day 5) fell due in the gap.

Once, late. The next wake-up time (day 5, 00:00 UTC) was stored on Umbrella's case row, so nothing was lost when the worker died. The restarted worker asked the database for every case whose wake-up time is now or earlier; day 5 had passed, so Umbrella was on the list, like an overdue item on a dated to-do list, and its first notice went out. The engine then wrote Umbrella's next wake-up time, so the following question did not find it again; each message also has a key made of the case, the stage and the version, and a second message with the same key is refused. Then Acme paid its $240 in full: nothing was owed, the case closed, and it never receives another reminder.

To explore at home: scheduled messages instead of a loop. The lab's worker polls: every second it asks the database which cases are due (a cron job would ask every few minutes). Try designing it without polling. Whenever the engine writes next_due_at, it also books one message on a queue, timed for that moment, that says only "look at this case" (Azure Service Bus scheduled messages, EventBridge Scheduler's one-time schedules and Google Cloud Tasks all do this). Nothing polls. Then work out what the loop was giving you for free: what happens to the booked message when Acme pays or the schedule changes; how an eleven-day wait fits a service whose limit is 15 minutes (SQS) or 30 days (Cloud Tasks); and what you watch instead of a heartbeat when there is no loop. The third piece built live: inbound.py. One model call classifies a customer's reply into one of six intents (a promise to pay, a dispute, a payment claim, a request to stop, a question, or something else), with a confidence and any date or amount it contains. Code then applies a fixed action for that intent. The model never changes a balance and never sends a message: a payment claim is recorded as a note, because only the ledger moves money; a dispute or a request to stop hands the case to a person; a promise pauses the case until the morning after the promised date. A confidence under 0.6 sends the reply to a person whatever the label. Because the model can only pick a row of this table, the worst a manipulated model can do is pick the wrong row, and every row can be undone.

The out-of-office: drop it, or let the model read it?

The lab sorts nothing: the console sends your text straight to its case, and POST /inbound finds the sender's open case or answers 404.

A collections address receives more than replies to reminders: bounces, automatic replies, questions meant for another team, spam and phishing. Most of it can be sorted by code before a model is involved, using what the email carries. A bounce is a delivery report and says so in its headers; an automatic reply is marked as one; a sender's domain either passes or fails its authentication check. The strongest signal is set when the reminder is sent: its reply address carries a token for that case (random, so nobody can guess another customer's), and a reply that comes back to that address belongs to that case without any reading at all. A message with no token, no thread and no open case for the sender goes to a person or another team.

Sorting first is fast, free and testable, and it keeps text the model shouldn't read away from it. The lab does none of this: the console posts a reply straight to one case, and POST /inbound only looks up the sender's address.

Read it, or at least its date. An out-of-office says when someone will be back, so the next reminder can wait for them instead of landing in an empty inbox. Dropping it is free and loses that date; reading it costs one model call. Tonight's triage harness gives out-of-office replies their own intent for this reason.

The lab's inbound step, built in class, is a first cut: one model call, then a fixed action in code. Production triage, tonight's build in dunning/triage/, has five steps, always in this order, each called by code:

  1. Read (the model): the reply becomes a structured reading: what kind of reply it is, the dates, amounts and references in it, and short quotes that support the reading.
  2. Match (code): the reading is matched to the customer's open invoices by exact lookup.
  3. Propose (the model): one action from a list code supplies, plus an optional draft reply.
  4. Check (code): every part of the proposal is tested against the reply text, the ledger and the policy.
  5. Gate (code): an action that can be undone runs now and is logged; one that can't waits for a person's approval; a failed check sends the reply to a person and nothing is sent.

The gate decides by one question: can the action be undone? Reversible actions run immediately, are recorded in the case's history, and a person can reverse them. They all reduce what the system does: pause, snooze, stop chasing, hand to a person, note a claim. Three things can't be undone and wait for a person's approval: a payment plan (a commitment), a change of contact (account details would go to a new address) and any reply to the customer (an email can't be recalled, and free text can promise things no check can see).

The result is an approval queue that holds only consequential decisions. The cost is accepted on purpose: a false promise to pay delays chasing by a few days, which is recoverable. The checks run before the gate, so a proposal that fails one (a plan whose instalments don't add up to the balance, say) never reaches the approval queue: it goes to a person as a failure, with the reason.

Step 2 · matchCode finds the invoice. Five rules, in order.

  1. An invoice number the customer wrote, if it is one of their open invoices.

  3. Else an amount that equals exactly one open balance.
  4. Else, if the customer has only one open invoice, that one.
  5. Else nobody guesses: no match, and a person looks.

The model pulls "INV 2041" or "TRX-5531" out of the text. Code looks it up. An invoice number that isn't this customer's is kept, and flagged.

Matching a reply to invoices is done by code, with rules ordered from most to least certain: an invoice number the customer wrote (only if it is one of their own open invoices), a payment reference found in the ledger, an amount equal to exactly one open balance, the customer's only open invoice, and otherwise no match. The model's part is only extraction: finding the invoice number or payment reference in messy text. Every proposal goes through eleven checks in code, grouped by the question they answer:

The problems a queue brings with it, and the standard answers:

  • Queues deliver at least once, so the same email can arrive twice. Each job carries an idempotency key (here, the email's message id) and a second copy is dropped.
  • A slow or failing model call is retried with backoff a few times, then sent to the dead-letter list.
  • A job holds a lease; if the worker takes longer than the lease, the queue gives the job to another worker. Make the lease longer than the slowest run or renew it, and rely on the key.
  • Two replies for the same case are processed one at a time, with a lock per case or by sending all of a case's jobs to the same worker.
  • Bursts are absorbed by the queue while a cap limits how many model calls run at once.
  • A reply that names no case is matched by a token in the reply-to address, then the email's thread headers, then the sender's address, and otherwise goes to a person.

Reference · Running itOutbound: a scheduler that only asks, an outbox, a sender

How the outbound path runs. Because reminders are driven by time, a scheduler loop (a background service, a worker process or a scheduled job) runs every few seconds. It claims the cases whose next look is due, each with a lease (a time limit on the claim) so two running copies never process the same case, and a claim from a crashed worker expires. Each case is evaluated as it is now, with the model drafting the words and code checking them.

When a message should go, the case update and the message are written in one database transaction; that message table is the outbox. A separate sender delivers outbox rows, passing each one's key, and retries failures. The channel's answer (delivered, bounced) comes back as an event through the same door as replies and payments. In the lab, worker.py is the loop, store.claim_due_cases holds a 60-second lease, and messages are keyed case:stage:version; writing the row stands in for sending.

Four common ways to run the outbound loop, each with its production habits. A cron job starts a short run every few minutes. Prevent two runs from overlapping with a lock or with claims that carry a lease, and query for everything due now rather than everything due in this minute, so a run missed while the host was down is caught up by the next one.
