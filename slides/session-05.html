Idea 1The fix has a name: idempotency

An action is idempotent when doing it twice has the same effect as doing it once. x = 5 is idempotent; x += 5 is not.

A cloakroom ticket. The desk writes down every ticket it has served. Show ticket 42: you get your coat. Show ticket 42 again: "coat 42, already handed back". Nobody walks out with two coats.

Key sent with the refundWhat the order API does
First try3fa9c2e1b7d0:0new key: pays $79.99, refund R-1a2b3c4d
After the crash3fa9c2e1b7d0:0, rebuiltknown key: returns R-1a2b3c4d, pays nothing

Deskhand's idempotency key is the run's id plus the action's place in the plan, so a restart rebuilds the same one.

Idea 2Start from the job, not the model

Keep it in code

  • Is $79.99 at most the order total?
  • Is it over the $50 limit?
  • What's in order O-48291?

Arithmetic, rules, lookups: exact, free, testable.

Give it to an LLM

  • What is this customer upset about?
  • Which policy section applies here?
  • Write a kind reply in plain words.

Messy language in, language out.

If a few lines of code can do it, an LLM only adds cost, delay and a way to be wrong.

Idea 2Three questions for any LLM idea

Volume

Does it happen a lot? 50 tickets a day is worth automating. 5 a month isn't.

Review

Does a person see it before it happens? Deskhand: a refund over $50 waits for a yes.

Check

Is it quick to tell if it's right? Deskhand's plan is three lines: seconds to check.

6 is strong. 3 or less usually isn't worth building. Review asks when someone looks; Check asks how long looking takes.

If a wrong answer can't be undone, don't let an LLM act on it alone.

Idea 2Your product team uses RICE: add the three questions

RICE: which idea goes first?

  • Reach: how many a month?
  • Impact: how much does each one gain?
  • Confidence: how sure are we of those two guesses?
  • Effort: how many person-months to build?

R × I × C ÷ E. The biggest number goes first.

What RICE never asks about an LLM

  • Review: does a person see it before it happens?
  • Check: is it quick to tell if it's right?
  • Undo: what can't be taken back, and who signs it?

Reach covers our volume question.

Mortgage approval: a big RICE score at a bank, and still 0 on the three questions.

RICE picks which idea to fund. The three questions tell you if it will still work with a model inside.

RecapThree things to remember

  1. One refund, paid once. A key built from saved state, remembered by the server. The framework decides where to resume; the key decides whether that is safe.
  2. Score the job before the model. Volume, review, check, and what can't be undone. Then take it apart step by step: code or model, what it reads, what it writes, who checks.
  3. At work, the platforms sell the plumbing. Logins, links to company systems, logs. The rules, the gate, the key and the evals stay yours, whatever you buy.
Which layer stops it? Take the worst thing a use case could do, and name what catches it: a rule, the gate, the key, or a check. If nothing does, don't build it yet.

Pre-readThe model asks, your code acts

With tool calling, you send the model a list of tools it may ask for. Instead of plain text, it can reply with a request: look up order O-48291. The model never runs anything. Your code reads the request and decides whether to run it.

The model fills in a request form: "refund $79.99 on order O-48291". Your code is the finance desk: it checks the form against the records, and over $50 a manager signs it first (Monday's gate). A filled-in form is not a payment.

Deskhand goes one step further: the model only writes a plan, and code calls both tools.

Pre-readWhat the model sees for a tool: a schema and a description

{"type": "function", "function": {
    "name": "lookup_order",
    "description": "Read-only. Fetch one order (items, total, status, …",
    "parameters": {"type": "object", "required": ["order_id"],
                   "properties": {"order_id": {"type": "string", …}}}}}
  • The schema is the form's layout: fields, types, which are required (Session 2's schema).
  • The description is the only manual the model reads. It decides when the model picks the tool.

The model can invent an order id or a negative amount. Check tool arguments like any untrusted user input.

Pre-readReal APIs misbehave, so ours does too

A chaos mode is a switch that makes the mock order API fail on purpose, so you can watch how Deskhand copes.

Deskhand's answer, from Monday's reference slides: wait 5 s per try, three tries, a longer pause before each, then give up with a name (16.5 s worst case). Retry a timeout or a 500. Never retry a 404: "order not found" is an answer.

ResilienceWait, try again, wait longer, then stop

A timeout is how long you wait for one call before you give up on it. Deskhand waits 5 seconds per try, tries three times, and pauses a little longer before each new try.

Try again

No answer in time, a dropped connection, a 500 from the server.

Don't

A 404, "order not found". That's an answer: asking again gets the same one.

ResilienceThe retry loop in nodes.py

A retry with backoff tries again after a pause, and pauses longer each time, so a struggling server gets room to recover.

ORDER_API_TIMEOUT_S = 5.0
ORDER_API_RETRIES = 2                    # after the first try: 3 tries in all
ORDER_API_BACKOFF_S = (0.5, 1.0)         # pause before try 2, before try 3
for attempt in range(ORDER_API_RETRIES + 1):   # nodes.py, _order_api_call
    if attempt > 0:
        time.sleep(ORDER_API_BACKOFF_S[attempt - 1])
    ...                                  # timeout or 5xx: note the code, try again
    return response                      # 2xx or 4xx: that's an answer

Worked numbersFlaky mode: how often do 3 tries still fail?

TriesChance that every try failed
10.5 = 50%
20.5 × 0.5 = 25%
3 (Deskhand's limit)0.5 × 0.5 × 0.5 = 12.5%: about 1 call in 8 still fails

T-1004 makes two calls, a lookup and a refund, so a whole run fails 1 − (7/8)² ≈ 23%: about 1 run in 4.

3 tries × 5 s, plus pauses of 0.5 s and 1.0 s = 16.5 s on paper before TOOL_ORDER_API_TIMEOUT. On Windows, localhost adds about 2 s per try.

In flaky mode the refund POST fails half the time too, and gets retried. Retrying a payment is safe only if the server can tell it's the same payment.

The fixBuild the key from the saved run

idempotency_key = f"{state.request_id}:{index}"   # nodes.py, execute_actions
refund = issue_refund.invoke({
    "order_id": state.order_data["order_id"],
    "amount_usd": state.resolution_plan.refund_amount_usd,
    "idempotency_key": idempotency_key,      # sent as a header
})
  • The key is the run's id plus the action's position in the plan, like 3fa9c2e1b7d0:0.
  • Same input, same output: a resumed run rebuilds the same key from saved state. Every write tool needs a key built this way.
  • Replay the crash: execute_actions runs again, the API knows the key, and returns the first refund. Money moves once.

Approval gateThe approval flow, end to end

The run waits in the database with approval_status = "pending". It survives a restart and resumes on the POST, minutes or days later. "No" is a normal ending, not an error.

LangGraphThe same loop, run by a library

LangGraph is a Python library that runs a graph of steps for you. You give it the nodes and where each can go next. It runs the loop, saves the state after every step, and can pause a run until a person answers.
