Idea 1The fix has a name: idempotency

An action is idempotent when doing it twice has the same effect as doing it once. x = 5 is idempotent; x += 5 is not.

A cloakroom ticket. The desk writes down every ticket it has served. Show ticket 42: you get your coat. Show ticket 42 again: "coat 42, already handed back". Nobody walks out with two coats.

Key sent with the refundWhat the order API does
First try3fa9c2e1b7d0:0new key: pays $79.99, refund R-1a2b3c4d
After the crash3fa9c2e1b7d0:0, rebuiltknown key: returns R-1a2b3c4d, pays nothing

Deskhand's idempotency key is the run's id plus the action's place in the plan, so a restart rebuilds the same one.

An action is idempotent when doing it twice has the same effect as doing it once. Setting x = 5 twice still leaves 5; adding 5 twice doesn't. Reading an order is idempotent by nature; creating a refund is not. An idempotency key fixes that: a name sent with the write, so "make a refund" becomes "make refund 3fa9c2e1b7d0:0", which can only exist once.

Two sides make it work. The server, here the mock order API, stores every key with the refund it produced, and returns the stored refund when a key comes back. The client, Deskhand, must send the identical key after a crash, so it builds the key only from things it saved: the run's id and the action's place in the plan (:0 is the first action). Stripe and most payment APIs work this way.

Next: which jobs are worth handing to an LLM, and what tool calling looks like at work

The halfway point. The first half was code: one refund, paid once. The second half has none. It asks which jobs are worth handing to an LLM, and what tool calling looks like at a company. Keep one task from your own job in mind; tonight's first step uses it.

Idea 2Start from the job, not the model

Keep it in code

  • Is $79.99 at most the order total?
  • Is it over the $50 limit?
  • What's in order O-48291?

Arithmetic, rules, lookups: exact, free, testable.

Give it to an LLM

  • What is this customer upset about?
  • Which policy section applies here?
  • Write a kind reply in plain words.

Messy language in, language out.

If a few lines of code can do it, an LLM only adds cost, delay and a way to be wrong.

Before choosing a model, look at the job. The left card is arithmetic, rules and lookups: is $79.99 at most the order total, is it over $50, what's in order O-48291. Code does these exactly, for free, and each one can be tested. The right card is language: what the customer is upset about, which policy section applies, a kind reply. That is what an LLM is for.

Deskhand has worked this way since Session 2. The model writes a plan, and rules.py, plain Python, decides whether its $79.99 is allowed. A useful habit: when someone proposes AI for a task, ask whether it is really a lookup or a rule. If a few lines of code can do it, the model only adds cost, delay and a way to be wrong.

Idea 2Three questions for any LLM idea

Volume

Does it happen a lot? 50 tickets a day is worth automating. 5 a month isn't.

Review

Does a person see it before it happens? Deskhand: a refund over $50 waits for a yes.

Check

Is it quick to tell if it's right? Deskhand's plan is three lines: seconds to check.

6 is strong. 3 or less usually isn't worth building. Review asks when someone looks; Check asks how long looking takes.

If a wrong answer can't be undone, don't let an LLM act on it alone.

Three questions to score any idea for an LLM, each 0, 1 or 2. Volume: does the job happen often enough to be worth automating? Review: does a person see the risky step before it takes effect? Check: is checking the result much quicker than doing the job yourself? Review and check sound alike. Review is about when someone looks; check is about how long looking takes. If checking takes as long as doing, nothing was saved.

A total of 6 is strong; 3 or less is usually not worth building. The scale is a rule of thumb for discussion, not a formula. The red box is the one hard rule: if a wrong answer can't be undone, the LLM never acts on it alone. A refund can't be undone, so Deskhand checks the rules before every one, and a person approves those over $50.

Four ideas. For each one, which of the three questions does it fail: volume, review, check, or none?

Idea 2Your product team uses RICE: add the three questions

RICE: which idea goes first?

  • Reach: how many a month?
  • Impact: how much does each one gain?
  • Confidence: how sure are we of those two guesses?
  • Effort: how many person-months to build?

R × I × C ÷ E. The biggest number goes first.

What RICE never asks about an LLM

  • Review: does a person see it before it happens?
  • Check: is it quick to tell if it's right?
  • Undo: what can't be taken back, and who signs it?

Reach covers our volume question.

Mortgage approval: a big RICE score at a bank, and still 0 on the three questions.

RICE picks which idea to fund. The three questions tell you if it will still work with a model inside.

Product teams often rank ideas with RICE, from Intercom's product team: Reach (how many a month), Impact (how much each one gains), Confidence (how sure you are of those two guesses) and Effort (person-months to build). Reach × Impact × Confidence ÷ Effort; the biggest number goes first.

Reach is our volume question. What RICE never asks is where LLM projects fail: does a person see it first, is it quick to check, what can't be undone? Mortgage approval shows why you need both: a bank could give it a big RICE score, and it still scores 0 on the three questions. RICE's confidence is about the reach and impact guesses, not about whether the model is right; that's the check question. For Deskhand, a RICE sheet would get effort most wrong: the model call takes a week, the rules, the gate, the key and the tests much longer.

The move that turns a job into a design: don't hand the whole job to a model. Split it into steps and ask four questions of each. Who does it, code or the model? What does it read? What does it write? How is a mistake caught?

In the late-invoices example, finding late invoices is a database query, so it's code. RecapThree things to remember

MechanicsThe tool-calling loop

Three of the four steps are your code. Only step 2 is the model, and its output is a request written as JSON.

The tool-calling loop, in four steps. 1: your code sends the conversation and the schemas of the tools the model may use. 2: the model chooses, and its output is a request written as JSON: call lookup_order with this order id. 3: your code runs the tool. ResilienceThe retry loop in nodes.py

A retry with backoff tries again after a pause, and pauses longer each time, so a struggling server gets room to recover.

ORDER_API_TIMEOUT_S = 5.0
ORDER_API_RETRIES = 2                    # after the first try: 3 tries in all
ORDER_API_BACKOFF_S = (0.5, 1.0)         # pause before try 2, before try 3
for attempt in range(ORDER_API_RETRIES + 1):   # nodes.py, _order_api_call
    if attempt > 0:
        time.sleep(ORDER_API_BACKOFF_S[attempt - 1])
    ...                                  # timeout or 5xx: note the code, try again
    return response                      # 2xx or 4xx: that's an answer

A retry with backoff tries again after a pause, and pauses longer each time, so a struggling server gets room to recover. Three constants set it up: a 5-second timeout per try, 2 retries after the first try (three tries in all), and pauses of 0.5 and 1.0 seconds before tries 2 and 3. In the loop, a timeout, a connection error or a 5xx status notes an error code and goes round again. A 2xx or a 4xx returns at once, because that's an answer.

A 404 isn't retried because asking again for an order that doesn't exist gets the same answer. When all three tries fail, the call ends with a named error, TOOL_ORDER_API_TIMEOUT or TOOL_ORDER_API_ERROR. A 4xx on the refund becomes TOOL_ORDER_API_ERROR with "refund rejected" in the detail.

A StateGraph is the dict of nodes plus the while loop. A checkpointer is save_state done for you after every step, like a save point in a game. interrupt() is Deskhand's PAUSE under another name.

LangGraph is the runner, not the logic: graph_lg.py wraps the same nodes, and nodes.py doesn't change. Set DESKHAND_RUNTIME=langgraph, or use Start · LangGraph in the lab's Setup, to run the service on it. Its checkpoints go to runs.langgraph.db.

Restarting stuck runs becomes invoke(None) on the run's thread, whose id is the request id.

What stays Deskhand's own matters more: the nodes, rules.py, the idempotency keys, the event log and the runs table. LangGraph knows where to continue a run. It doesn't know whether a refund is safe to repeat. await_approval is its own node because a resumed node re-runs from the top: with interrupt() inside the gate, approval.required would fire twice.
